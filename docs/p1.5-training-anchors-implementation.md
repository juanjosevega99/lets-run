# P1.5 implementation spec — training-derived performance anchors

> **Audience:** an implementing agent/model with NO prior context. Third spec in the
> series (`docs/p0-checkin-implementation.md`, `docs/p1-forecast-implementation.md`).
> **Hard dependency: P1 must be implemented first** — this spec produces additional
> `PerformanceObservation`s for P1's `performanceState.ts`; it is meaningless alone.
> Written 2026-07-19; verify anchors before editing.

---

## 1. Why

P1's anchor model is only as good as its most recent trustworthy observation, and
races are rare: the athlete's last max-effort race is from 2022, and the next tune-up
may be months away. Meanwhile the database holds **906+ activities with streams**
(92% coverage: per-point time/distance/altitude/HR) in `activity_streams`. Hard
training efforts — a 5K time-trial, a sustained tempo, even a hard parkrun logged as
a normal run — are measurable performance observations sitting unused. Mining them:

- gives the current-shape estimate **fresh anchors between races** (the single
  biggest accuracy lever identified by the backtest: fresh-anchor MAE ≈ 1.7% vs
  +10…41% stale);
- makes the P1 forecast's milestone loop automatic — a hard test effort shows up as
  a new anchor without Juan filing anything;
- densifies the observation set for calibrating the CTL-bridge exponent k (P1 §3.3
  currently has ~6 usable race points).

## 2. Design overview

```
activity_streams ──► effort scan (per activity, pure) ──► candidate windows
                                                            │  guards: HR near-max,
                                                            │  coverage, GPS sanity
                                                            ▼
                                    performance_observation rows (source='training')
                                                            │
                     P1 performanceState (source-agnostic) ◄─┘   races remain source='race'
```

One pure module does the detection; a thin incremental job persists observations;
P1's loaders union race- and training-sourced observations with different confidence
weights. **No LLM, no new dependencies, no ML.**

## 3. The detection algorithm (`src/deterministic/effortScan.ts`, new, pure)

### 3.1 Inputs

```ts
export interface EffortScanInput {
  timeS: number[];                    // from activity_streams (parallel arrays)
  distanceM: (number | null)[];
  altitudeM: (number | null)[];
  heartrate: (number | null)[];
  hrProfile: { hrMax: number; hrRest: number };
}
export interface DetectedEffort {
  durationS: number;                  // the window that fired
  flatEquivalentDistanceM: number;    // GAP-adjusted (Minetti) distance
  meanHrPctMax: number;
  hrCoverage: number;                 // fraction of window samples with HR
  vdot: number;                       // via vdotFromRace(flatEquivDistance, duration)
  startIndex: number; endIndex: number;
}
export function scanForMaxEfforts(x: EffortScanInput): DetectedEffort[]
```

### 3.2 Windows

Fixed candidate durations: **12, 20, 30, 45 minutes** (≈ efforts between 3K and
~10K-race intensity for this athlete; shorter windows are too anaerobic for the
VDOT curve to be trustworthy, longer sustained maximal efforts in training are
rare and will usually be races anyway). For each duration D, slide over the stream
(step ≈ 30 s) and compute for each window:

- **flat-equivalent distance**: sum per-segment `Δdistance × gapFactor(grade)⁻¹`…
  careful with direction: Minetti `gapFactor(i) = C(i)/C(0)` is the *energy* ratio;
  flat-equivalent distance = Σ `Δd × gapFactor(grade)` (uphill meters count for
  more). Reuse `costOfGrade`/`gapFactor` from `src/deterministic/minetti.ts`; clamp
  per-segment grade to ±0.30 and segment speed to ≤ 6.5 m/s (GPS teleport guard).
- **mean HR % max** over samples present; **HR coverage** = samples with HR / total.
- Altitude smoothing: 5-point moving median on `altitudeM` before grade computation
  (raw barometric/GPS altitude noise otherwise manufactures grade).

Take, per duration, the window with the highest flat-equivalent speed; then dedupe
across durations (drop a shorter window fully contained in a longer accepted one —
keep both only if the shorter one's VDOT exceeds the longer's by > 1.5 points).

### 3.3 Acceptance guards (all must pass — reject silently otherwise)

| Guard | Threshold | Why |
|---|---|---|
| HR coverage in window | ≥ 0.90 | no HR → can't distinguish maximal from moderate |
| Mean HR | ≥ 88% of HR-max | near-threshold-or-above evidence of real effort |
| Last-third HR vs first-third | ≥ −2 bpm (non-falling) | a genuine sustained effort holds or drifts up; falling HR = surge-then-jog |
| Pace stability | coefficient of variation of 60 s split speeds ≤ 0.15 | interval sessions with jog recoveries must not read as one sustained effort |
| Distance stream present | ≥ 95% of samples | treadmill/no-GPS runs excluded in v1 |
| Duration sanity | window fully inside activity; no time gap > 60 s inside window | paused watches |

These reject most workouts — **by design**. A missed anchor costs nothing (the
model keeps its previous anchor); a false anchor poisons the estimate. Precision
over recall, hard-coded stance.

### 3.4 VDOT + confidence mapping

`vdot = vdotFromRace(flatEquivalentDistanceM, durationS)` (existing function).
Confidence for P1's weighting: `"low"` by default; `"medium"` when duration ≥ 20 min
AND HR coverage ≥ 0.95 AND mean HR ≥ 92% max. Training efforts never reach `"high"`
(reserved for chip-timed max-effort races). Rationale: a training effort has no
guarantee of true maximality; the confidence ladder encodes that skepticism.

## 4. Persistence (migration 007)

```sql
create table performance_observation (
  id serial primary key,
  source text not null check (source in ('race', 'training')),
  activity_id bigint references activities(id) on delete cascade,
  race_id integer references races(id) on delete cascade,
  observed_on date not null,
  vdot double precision not null,
  duration_s integer not null,
  flat_equivalent_distance_m double precision not null,
  confidence text not null check (confidence in ('high', 'medium', 'low')),
  detail jsonb,                       -- window meta: hr pct, coverage, indices
  created_at timestamptz not null default now(),
  unique (source, activity_id, duration_s)
);
```

Races are **not** copied into this table in v1 — P1's loader unions
`races (is_max_effort)` with this table at read time (one function:
`loadObservations(sql, cutoff)` in `src/backtest/history.ts`), keeping `races` the
single source of truth for race data. If P1 was implemented with a different loader
shape, adapt — the union point is the contract.

## 5. The scan job

- `npm run anchors:scan` (`src/fitness/anchorScanCli.ts`): incremental — scan only
  run activities with streams, `start_date` newer than the newest
  `performance_observation.created_at`'s activity (or `--all` for the one-time
  backfill). Per activity: load streams, run `scanForMaxEfforts`, upsert accepted
  efforts. Log per-activity outcomes at one line each ("accepted 20 min VDOT 44.1" /
  silent skip).
- Wire into the refresh pipeline **after** fitness, **before** current-shape
  (`src/pipeline/refresh.ts` STEPS) — new activities get scanned the same press.
- Backtest leak-proofing: predictors must see only observations from activities
  strictly before the cutoff. Since observations carry `observed_on`, the loader
  filters on it (same pattern as `priorRaces`).

## 6. Expected effect on HIS data (verifiable during implementation)

The 2025-11-23 activity — 5.0 km at 4:25/km, avg HR 189 (94% of max 201) — is a
textbook detectable effort sitting in the DB right now. The backfill should surface
it as a ~VDOT-mid-40s medium-confidence observation dated 2025-11-23, which is **3
years fresher than the current best anchor** (2022 races). Use it as the acceptance
smoke test: if the scan doesn't find it, the guards are mistuned; if it finds
dozens of similar ones in easy-run months, the guards are too loose.

## 7. Tests (pure; synthetic streams built in-test)

- Steady 20 min @ 92% HR-max, flat, clean streams → exactly one accepted effort,
  VDOT ≈ analytic expectation (tolerance ±0.5).
- Same effort on a 5% constant grade → flat-equivalent distance > raw distance;
  VDOT within ±1 of the flat case (GAP normalization works).
- 6×(2 min hard / 2 min jog) intervals → **rejected** (pace CV guard).
- Hard 20 min with HR stream missing → rejected; with 85% coverage → rejected.
- GPS teleport (one 200 m sample) → segment clamped, window survives or rejects
  deterministically (pin which).
- Paused watch (90 s time gap) → window spanning the gap rejected.
- Dedupe: 30 min effort containing the best 20 min → one observation unless the
  20 min VDOT exceeds by > 1.5.
- Confidence ladder thresholds pinned.

## 8. Runbook + DoD

```bash
npm run migrate                          # 007
npm run anchors:scan -- --all            # one-time backfill; expect the 2025-11-23 hit
npm run backtest                         # anchored-v1 must now show fresher anchors in provenance
npm run predict                          # anchor date should jump from 2022 → newest accepted effort
npm run typecheck && npm test
```

Done when: the smoke-test effort (§6) is detected with plausible VDOT; backtest
fresh-bucket population grows (report shows more fresh-bucket predictions);
`npm run predict` provenance cites a training anchor with its confidence; guards'
constants are pinned by tests; NEXT_STEPS updated.

## 9. Out of scope

- Treadmill/no-GPS efforts, power meters, cadence (future).
- Auto-classifying *planned* session compliance from streams (belongs to the P0
  follow-ups, different problem).
- Any change to the plan generator or review controller.
- Tuning the CTL-bridge k beyond what denser observations naturally give P1.
